# GreenPulse

### 面向绿色 Token 智算工厂的 AI 原生能源-算力协同编排平台

*让 AI 负荷主动匹配绿电时序，构建下一代绿色 AI 数据中心。*

</div>

---

## 项目一句话

GreenPulse 是一个面向下一代绿色 AI 数据中心的能源-算力-AI 协同调度框架：融合多时间尺度的绿电预测、电价、碳强度、GPU 资源与 AI 任务画像，在保障业务 SLA 与任务 Deadline 的前提下，将高耗能弹性任务主动调度到低碳绿电窗口，实现更低碳、更低成本、更高效的绿色 Token 生产。

> 传统调度器问：**现在哪块 GPU 空闲？**
>
> GreenPulse 问：**这个 AI 任务应该在什么时候、用哪部分算力运行，才能生产更绿色的 Token？**

---

## 面向的命题挑战

数据中心未来不只是堆叠算力硬件的基础设施，而是一座低碳高效、智能调度、可量产运营的**绿色 Token 智能工厂**。GreenPulse 针对四大真实挑战给出回应：

| 命题挑战 | GreenPulse 的回应 |
|---|---|
| **① 绿色能耗匹配难**：风光绿电间歇波动，无法适配 7×24 小时 AI 算力生产 | 把可延迟 AI 任务视为"虚拟储能"——不强求绿电匹配负荷，而是让弹性负荷主动跟随绿电窗口 |
| **② 算力能效产出低**：调度零散、批处理不合理、空载率高、散热供电损耗 | 任务分级批处理(刚性/半弹性/弹性画像) + 分时 PUE 建模,能耗核算覆盖设施级损耗 |
| **③ AI 调度协同弱**：高能耗任务与电网高峰、火电时段错配,缺乏智能节能调度 | 碳/价/绿电三信号驱动的智能调度大脑,联合优化启动、延迟与资源分配 |
| **④ 产品商业化缺失**：无统一碳溯源、能效分级与定价规则 | 每个调度决策落结构化记录,逐批次 gCO2/token 可溯源,支撑绿色 Token 台账与能效分级 |

---

## 核心思想

与其强行要求波动的绿电去持续匹配 7×24 小时 AI 负荷，不如让具备弹性的 AI 负荷主动跟随绿电窗口运行。

任务画像三分类：

| 类别 | 示例 | 调度自由度 |
|---|---|---|
| 刚性（rigid） | 在线推理、实时 API | **SLA 保护，到达即服务，绝不为节能延迟** |
| 半弹性（semi） | 批量推理、评测、Embedding | 小时级时移 |
| 弹性（elastic） | 训练、微调、离线推理 | 日级时移（Deadline 约束内） |

调度优化目标：

```text
最小化：α·用电成本 + β·碳排放 + γ·SLA违约惩罚 + δ·峰值功率惩罚 + ε·迁移/重启成本
```

约束：SLA、任务 Deadline、GPU 容量、Pod 功率预算、绿电可用性。所有权重与参数来自 `configs/default.yaml` 单一配置文件（γ 远大于 β：SLA 保底是铁律）。

## 快速开始

```bash
pip install -e ".[dev]"
make demo    # 一条命令:全合成信号仿真回放 + 六策略对照表(无外网/无 GPU/无密钥)
make test    # 测试套件(契约测试/故障注入/确定性双跑)
make lint    # 代码检查
```

`make demo` 在一个虚拟 AI 数据中心（3 个 GPU Pod、48 小时、15 分钟步距）上回放三类任务的调度过程，输出对照表，并在 `results/` 落盘实验记录与逐决策 JSONL 日志。

### Demo 输出示例

```text
====================================================================================
GreenPulse 仿真对照表 —【合成场景,非实测】
====================================================================================
policy           carbon_gco2   cost    green_rate  peak_kw  rigid_slo  gco2/token
------------------------------------------------------------------------------------
carbon_agnostic  <基准>        ...     ...         ...      1.000      ...
best_static      ...           ...     ...         ...      1.000      ...
price_only       ...           ...     ...         ...      1.000      ...
carbon_only      ...           ...     ...         ...      1.000      ...
oracle*          ...           ...     ...         ...      ...        ...
carbon_aware     ...           ...     ...         ...      1.000      ...
------------------------------------------------------------------------------------
* oracle = 事后完美预测的理论上界,用于上限分析,不代表产品收益
```

对照策略说明：

| 策略 | 含义 |
|---|---|
| carbon_agnostic | 性能优先：有资源即启动（对照基准，也是 `ecoModeOff` 逃生开关的行为） |
| best_static | 固定时间窗运行弹性任务 |
| price_only | 只跟随低电价窗口 |
| carbon_only | 只跟随低碳窗口 |
| oracle | 事后完美预测（节碳理论上界） |
| **carbon_aware** | **GreenPulse：绿电预报驱动,联合考虑碳/价/SLA** |

### 每个决策可解释、可回放

`results/decisions_*.jsonl` 中每条调度决策都包含：任务、动作、时间窗、决策时刻的信号快照（碳强度含口径标签、电价、绿电预报）、目标函数各项贡献值、被拒的替代动作。给定同一快照与配置，决策可确定性重放——"为什么把任务挪到 12:00"可以逐项拆账。

## 架构与代码结构

```text
green-token-orchestrator/
├── configs/default.yaml        # 单一配置真源:权重、Pod 定义、信号源选择
├── greenpulse/
│   ├── signal/                 # 信号层:碳强度/绿电预报/电价 Provider 抽象 + 注册表
│   │                           #   合成曲线与 static-json 文件是同一接口的两个实现,
│   │                           #   接入真实数据源 = 新增 1 个文件 + 改 1 行配置
│   ├── sim/                    # 仿真内核:时钟、Pod、任务队列、分时 PUE、决策记录
│   │                           #   调度器只能看到决策时刻之前的信号(防"偷看未来")
│   ├── policy/                 # 调度策略:五个对照基线 + carbon_aware 调度器
│   ├── eval/                   # 评测与留痕:实验记录 CSV(git SHA + 配置哈希)
│   ├── executors/              # 执行层适配器接口(Kueue/KEDA/调度器插件/vLLM)
│   └── demo.py                 # make demo 入口
├── deploy/                     # 真实集群插入点说明
├── tests/                      # 契约测试、故障注入、确定性双跑
└── docs/                       # 项目计划、竞赛命题、数据许可等文档
```

三模块协同（对应能力架构图）：

1. **绿色能耗智能感知**：绿电出力预报、电网碳强度、分时电价 → 可调度的时间窗口与功率边界；
2. **算力能效智能感知**：GPU Pod 状态、任务画像（GPU 需求/时长/功耗/Deadline/Token 产量）→ 容量与功率约束；
3. **AI 协同调度大脑**：联合优化任务启动、延迟与资源分配,输出可解释的滚动执行计划。

信号断供时系统显式降级为性能优先模式并在决策记录中标注——绝不基于编造或过期的信号做"绿色"决策；`ecoModeOff` 一键关闭全部碳感知行为。

## 对接真实 AI 数据中心

当前 MVP 是 Digital Twin 仿真原型，但架构从第一天就为真实化留门：信号与执行都走抽象接口，仿真实现与真实实现完全同构，替换实现即可接入生产环境。

### 信号侧（数据进来）

`signal/` 的 Provider 抽象让接入真实源 = 新增 1 个文件 + 改 1 行配置：

| 信号 | 真实数据源 |
|---|---|
| 碳强度 / 电价 | Electricity Maps、WattTime（注意商业条款与中国区覆盖）；国内路径：省级电网分时数据、电力交易中心公开数据 |
| 绿电出力 | 场站 SCADA / 功率预测系统 API，或数据中心绿电采购计量数据 |
| 集群实时能耗 | Kepler / Scaphandre（节点级）、NVIDIA DCGM（GPU 级功耗遥测）——让任务功耗画像从估算变实测 |

### 执行侧（决策出去）

`greenpulse/executors/base.py` 中四个接口对应真实集群的四个插入点：

| 接口 | 真实宿主 | 对接机制 |
|---|---|---|
| AdmissionCheckAdapter | Kueue | AdmissionCheck 控制器：批任务在低碳窗口到来前保持 Pending |
| ExternalScalerAdapter | KEDA | external scaler gRPC 服务：按碳信号伸缩弹性推理副本 |
| SchedulerScorePlugin | kube-scheduler | Scheduling Framework Score 扩展点：跨站点/机房碳效打分 |
| InferenceRouterScorer | vLLM / llm-d | 请求级路由打分：token 级调度旋钮的落点 |

调度大脑与适配器之间通过中性介质解耦：信号写成 K8s ConfigMap + Prometheus 指标（前缀 `gto_`），适配器只消费这个介质，不直接感知上游数据源。

### 真实对接需额外处理的三类问题

1. **执行是异步且会失败的**：真实集群里决策下发后要等调度、可能被抢占。适配器需要状态回读（desired vs actual）与幂等重试，失败时保持现状、不振荡；
2. **信号时效**：ConfigMap 里的碳强度可能过期——现有的时龄校验与"显式降级 + 标注"逻辑可原样复用；
3. **测量闭环**：gCO2/token 的分子分母改为实测（DCGM 功耗 × 电网碳强度 / 推理服务 token 计数），绿色 Token 台账从机制演示升级为可审计产品。

**推进顺序**：先只读信号真实化（零风险）→ KEDA scaler（只碰副本数，影响面最小）→ Kueue / 调度器插件（碰任务准入，需在测试集群充分演练）。

## 当前状态与 Roadmap

当前为 Digital Twin 仿真原型（MVP）：先在可控的虚拟数据中心里验证调度逻辑、量化收益,执行层接口为接入真实集群（Kubernetes/Kueue/KEDA/vLLM）预留。

- [x] 信号层 Provider 抽象 + 合成/文件双实现
- [x] 仿真内核：3 虚拟 Pod、三类任务、分时 PUE、可解释决策记录
- [x] 五基线对照 + carbon_aware 调度器 + `ecoModeOff` 逃生开关
- [x] 实验留痕与一条命令 demo
- [ ] 节碳上限分析（oracle 在目标电网曲线下的理论上界）与评测协议定稿
- [ ] 滚动时域多目标调度器（MILP/启发式）
- [ ] Token 级碳感知模型路由（大/小模型两档,等质量约束下降低 gCO2/token）
- [ ] 路演可视化大屏与 Grafana 面板
- [ ] 绿色 Token 台账：批次级 gCO2/token 标签 + 能效分级 + 全链路溯源

## 愿景

AI 不应只优化计算本身，AI 也应该根据能源供给来编排计算。

GreenPulse 希望成为未来绿色 Token 智算工厂的智能调度层，推动 AI 数据中心从"售卖 GPU 资源"升级为"经营低碳数字产能"，实现每一枚 Token 更低碳、更廉价、更稳定、更具商业化价值。
