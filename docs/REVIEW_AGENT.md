# 独立评审代理章程(REVIEW_AGENT)

GreenPulse。生效 2026-07-29。

本文件定义一个**独立于开发过程的常设评审代理**:它在每个关键节点对"整个过程"(代码、文档、数字、决策)做对抗式审查。它可以由 AI 代理执行(推荐,附提示词模板),也可以由未参与该项工作的队员执行;两者遵循同一份章程。**独立的定义:评审者没有写过被评审的那部分产物。自评无效,同一条产线的同伴评审不算独立。**

设立依据:姊妹项目的复盘结论——同一仓库四次发生"绿色测试为坏行为背书",共同点是断言比声称低一个层级,且**每一次都是独立评审发现的,没有一次是作者自查发现的**。这不是个人疏忽,是结构性规律:作者对自己的产物有确认偏误,独立评审是唯一被证实有效的解药。

---

## 1. 触发点(何时评审)

| 触发 | 评审范围 | 阻塞性 |
|---|---|---|
| 每个阶段准出(P0 / S / O / A / R——含未命名 Gate 的阶段,与 PLAN §"所有阶段阻塞式验收"对应) | 该阶段全部准出判据 + 状态列双向复核 | **阻塞**:评审未通过,阶段不交接 |
| 任何新增测试 | R0.2 红证是否存在;断言层级是否与声称同级 | **阻塞**:无红证不接收 |
| 任何对外材料定稿(README 更新、PPT、报告、答辩稿) | 数字四件套;溯源反查;数据性质标注 | **阻塞** |
| 任何冻结后变更申请 | fatal-defect 判据;四件套(红证/CHANGELOG/重跑/全局更新) | **阻塞**(章程即 RISKS §2 的"独立批准人") |
| 每周(轻量) | 范围蔓延信号(RISKS R6 的 Trigger)、文档与树的一致性抽查 | 非阻塞,出周报 |

## 2. 评审方法:STORM 式视角轮换

每次 Gate 评审,评审代理按 [`IDEA_REVIEW.md`](IDEA_REVIEW.md) 的六视角轮换质询,每视角至少提出 3 个"若答不上则该项降级"的问题;问题必须落在证据上(树里的代码、实验记录的行、带 URL 的外部来源),不接受"我们打算"作为答案。六视角与各自的常备武器:

- **基本事实核查员**:文档声称 vs 树的双向 diff(假 DONE 与假 PLANNED 同罪);数字→实验记录反查。
- **赛道/商业评委**:交付物与 `COMPETITION_BRIEF.md` 的要求对齐;叙事是否被 Gate S 的上限数字支撑。
- **技术评委**:评测协议是否被绕过(协议外的数字出现在任何材料 = 最高严重度);相关工作对照表是否诚实。
- **世纪互联工程师**:可插拔性验收(新 Provider = 1 文件 + 1 配置行 + 0 下游改动,用 `git diff --stat` 实证);接口是否泄漏供应商/存储假设。
- **竞品**:每个"我们的差异化"声明是否仍然成立(竞品仓库在动,GAR/llm-d 都在活跃开发)。
- **运维/SRE**:DFR 矩阵的 PINNED/xfail/Observed 空格三计数;降级路径是否演练过。

## 3. 常备检查清单(每次 Gate 全量过)

1. **断言层级审计**:抽取本阶段新增的全部测试,逐个回答"如果被测行为是坏的,这个测试会红吗";答不上的记 CONFIRMED 缺陷。
2. **口径纪律扫描**:全库 grep 收益类数字,核对四件套(口径/基线/数据版本/SLO 代价)(ENGINEERING_RULES R3.1)。
3. **状态列双向复核**:DESIGN_STANDARDS 裁决表与 PLAN 判据逐行对树验证,双向(防假 DONE 也防假 PLANNED)。
4. **前视泄漏专项**:调度器可见信号窗口 ≤ 决策时刻的守护测试存在且做过删守卫验证(DFR DEP-4.4)。
5. **溯源抽查**:随机抽 5 个对外数字,反查实验记录行(SHA + config hash);判定标准与 PLAN R-X1 一致——**5/5 全部反查成功才通过,任一失败即不通过**。
6. **许可红线**:DATA_LICENSES 三条红线(AGPL 零 vendor / 数据快照零入库 / 内部材料隔离)。
7. **决策可解释抽查**:随机抽 3 条调度决策记录,核对 PLAN A-X3 的必含字段(任务、动作、时窗、信号快照、各目标项贡献值、被拒替代动作及其目标值)——**缺任一字段即记缺陷**;字段齐全但贡献值与目标函数定义对不上账的,记 FATAL。

## 4. 输出格式(强制)

评审产出为结构化 findings 列表,按严重度排序,追加到 `docs/reviews/<date>-<gate>.md`:

```
- id: <gate>-<序号>
  severity: FATAL | MAJOR | MINOR
  claim: <被评审方声称什么>
  evidence: <评审者实际看到什么(命令输出/文件行/URL)>
  verdict: CONFIRMED(评审者亲手复现)| PLAUSIBLE(未复现,须作者反证)
  required_action: <可判定的关闭条件,不是"改进">
```

规则:**无 evidence 的 finding 不许写**(评审代理自己也受 R0.1 约束——判定必须正向断言、可复核);CONFIRMED 的 FATAL 未关闭,Gate 不通过;findings 的关闭由**下一次**评审验证,不由作者自宣。

## 5. AI 代理执行的提示词模板

每次评审启动一个**全新会话**的代理(不带开发会话的上下文——上下文共享会继承作者的确认偏误),输入只给:仓库快照、本章程、被评审阶段的判据表。模板:

> 你是 GreenPulse 的独立评审代理,与开发过程无利益关联。你的唯一目标是**证伪**:被评审方声称已满足 <Gate X> 的判据 <列表>,请逐条尝试推翻。规则:(1) 每个结论必须附你亲手取得的证据(运行的命令与输出、读到的文件与行号);(2) 区分 CONFIRMED(你复现了)与 PLAUSIBLE(你怀疑但未复现);(3) 特别检查:断言层级(测试断言的量 vs 声称保证的量)、数字四件套、状态列与树的双向一致、前视泄漏守护、许可三红线;(4) 输出按 §4 格式;(5) 不确定时倾向报告——漏报一个真缺陷的代价远高于误报。禁止:提出与判据无关的风格意见;把"我会这样做"写进 findings。

多代理增强(资源允许时,参照 STORM 的并行视角):每视角一个独立代理并行质询,汇总去重后再做一轮"魔鬼代言人"——专查所有代理都没碰过的判据与文件(Co-STORM Moderator 机制)。

## 6. 对评审代理自身的约束

- 评审代理的 findings 也留痕入库(`docs/reviews/`),接受"评审的评审":每个里程碑复盘一次误报率与漏报事故。
- 评审代理不写产品代码、不给修复方案的实现(可以指出关闭条件);写了就丧失下一轮对该部分的独立性。
- **这个流程必须能说"不"。** 一个从未拦下过任何 Gate 的评审流程不是控制,是仪式(姊妹项目冻结政策原话,同样适用于此)。
